01 The problem

A wiki nobody trusts is worse than no wiki.

Three failures do the damage, and none of them announces itself. Documentation drifts from the code silently. Nobody can tell which pages were ever read by a human. And a reviewer's correction dies in a comment thread that no engineer subscribes to.

01

Drift is invisible

A page describing a service that was refactored last quarter looks exactly like a page that is still true. Nothing in the wiki knows what code a page came from, so nothing can notice when that code moves.

02

Approval is folklore

"Someone reviewed this" is a thing people remember, not a thing the system records. And when the page is edited afterwards, the memory survives the edit.

03

Feedback has nowhere to go

A reviewer who spots an error comments on the page. The page is not the source, so the comment has to be carried into the repo by hand, by someone who saw it. Usually nobody does.

02 The lifecycle

Five stages, three kinds of actor.

A model generates and rewrites and opens pull requests. A human approves and comments in Confluence. The CLI carries each gesture between the repo and the space. The split is the design: no model ever calls the Confluence API, so nothing a model does can change a page there.

The one-way rule

The repo is the source of truth

A page edited by hand in Confluence is overwritten the next time its markdown changes, and DocuMe never reads a page body back as content. That is the design, not a limitation: everything that reaches a page went through a pull request first.

Everything a reviewer adds that is not body text — labels, comments — travels the other way and lands in the repo as state or as an inbox item.

Two consequences, stated up front
  • publish --prune deletes pages whose markdown is gone. It asks first, needs a terminal, and refuses to run in CI.
  • A space DocuMe writes into should hold nothing but DocuMe's output. Start with a fresh empty space.
  • Machine edits are free: the injected banner is excluded from the content hash, so a new publish date never costs an approval.
03 Two tiers

Deterministic where it must be, generative where it helps.

The boundary is enforced, not advisory: only the CLI holds credentials, and every skill's output is a pull request a human reads before anything publishes.

04 Approval and drift

Two independent questions, tracked two different ways.

A page can be approved and drifted at the same time. That combination is exactly the one worth finding: somebody signed off on a description that is no longer true.

Approval

Has a human read this page?

Answered by a label a reviewer adds in Confluence, recorded into state.json against the page version it was approved at. Invalidated by a content change: DocuMe removes the label, archives the approval to history, and moves the page to needs-review.

The hash is taken over the converted body before the banner is injected, so editing a sentence invalidates and a new publish date does not. Reparenting does not either: where a page hangs is not what a reviewer approved.

Drift

Has the code this page describes moved?

Answered by diffing two revisions against each page's sources globs. The baseline is the commit the wiki content was last generated against, not the commit it was last published from — using the publish sha would report zero drift on any repo that publishes on every merge.

Marking is labels and a dashboard row, never a page-body edit. Editing bodies to add a staleness banner would bump every page version and revoke every approval in the space on the first nightly run.

An honest field approvedBy reads unknown by design. Confluence Cloud exposes no label author anywhere the API can reach it, and filling the field with the account DocuMe authenticates as would put a fabricated approver into an audit trail. The label itself is the gesture that counts.
05 The converter

Fail loud, or publish a page that quietly lost a section.

A custom Markdig renderer emits Confluence storage format directly. Not markdown → HTML → regex: storage format is not HTML, and every layer of that pipeline loses something the next one cannot recover.

Converts

Silent

The overwhelming majority. Headings, GFM tables, code macros with language mapping, GitHub alert panels, task lists, internal links resolved by title, images with widths, mermaid rendered to SVG attachments.

Degrades

Converts, and says so

Seven named codes, each reported per page with the dialect that triggered it. Storage format cannot express the construct, so the alternative to a warning is a quiet difference between the markdown and the page.

Fails

The page does not convert

Reserved for constructs where guessing would publish something wrong: an unknown diagram dialect, raw inline HTML, an unrecognized fence attribute. Better a red build than a silent hole.

The contract

28 hand-reviewed golden cases

Each case is a markdown file and the storage format it must produce, reviewed by hand once and asserted forever. A golden is never regenerated to make a failing test pass — the diff goes to a human, because a converter that rewrites its own expectations has no contract at all.

Dogfooding

DocuMe's own wiki clears the strict bar

Zero failures and zero degradations, with no accepted losses. A tool that documents itself using constructs it converts badly is not making a good argument. The suite fails when someone edits a page past that bar.

06 Automation

Six workflows, and every one of them writes through a pull request.

Scaffolded by docume init. Each adds the package feed, runs dotnet tool restore and then the CLI through the repo-local manifest, so a workflow and a laptop run the same pinned version.

WorkflowFires onDoesCredentials
docs-publish.yml push to the default branch, wiki paths Publishes what changed since the last published sha, then refreshes the dashboard Confluence
docs-sync.yml every six hours, plus manual Reads labels and comments; opens a docs/sync PR when state changed Confluence
docs-drift.yml workflow_run after your deploy Labels the affected pages stale. Never edits a page body Confluence
docs-drift-pr.yml every pull request Comments with the wiki pages this PR's code changes affect, and exits 0 None
docs-refresh.yml nightly at 03:00, plus manual Runs /docs-refresh when drift is reported Model key only
docs-feedback.yml new inbox items on the default branch Runs /docs-feedback on the untriaged comments Model key only

Why the two drift workflows differ

docs-drift-pr.yml is advisory: it comments and exits 0, because blocking a code pull request on documentation is how teams learn to bypass documentation. docs-drift.yml is the one that marks, and it fires after a deploy, when the code is real.

Why the token is split

The workflow with the widest trigger — one that runs on every contributor's branch — never sees the publishing token. Neither do the two unsupervised model runs: a skill's output is a pull request, so only the CLI writes to Confluence and the credential stays out of the job a model drives.

07 Untrusted input

A comment is a claim to verify, never an instruction to follow.

Confluence page bodies and comments come from outside the trust boundary, and the skills that read them are told so in as many words. Every inbox item is checked against the source. A comment asking for a credential, a link, or a change to another page is not acted on.

It is quoted verbatim in the pull request body, under its own heading, so a human decides what to do about whoever wrote it — and the item is triaged on whatever factual content it has left. Nothing a reviewer wrote is echoed into a page body, which is the whole point: a page is generated from code, not from comments.

Three verdicts, three different replies
  • The claim held — the page is fixed, and the reply says what changed.
  • The code contradicts it — declined, and the reply carries the citation that settles it.
  • The code cannot settle it — a product decision, an intent, code in another repo — recorded in _meta/GAPS.md for the team, and the reply says so.

The third route is the one that costs a reviewer when it is skipped. An unsettled claim filed as a decline tells them the page was checked against the code and is staying as it is, about a point nothing checked.

Credentials Two environment variables, and nowhere else. Never in docume.json, which is committed; never on the command line, which lands in shell history. A 401 or 403 is a hard stop with a token-expiry message rather than a retry — retrying a rejected credential only wastes the rate limit. Backoff is for 429 and 5xx.

09 Where it stands

Feature-complete through M6. Adoption and a second target come next.

DocuMe is built against a milestone plan, and the plan is in the repository. This is where the work actually is, not where it is hoped to be.

MilestoneScopeState
M0 – M6 Solution and config, the converter and its golden corpus, the Confluence client and publish pipeline, labels and approval, comments and replies, drift and the dashboard, the plugin and the release workflow Built, green
M7a The publication-target seam: a target discriminator in config, capability declaration with loud refusals, interfaces at the five reader and executor boundaries. No second implementation Planned
M7 Adoption on a real wiki: init --adopt, state migration, sources across the existing pages, workflows installed, team onboarding Planned
M8 A GitHub-native target: PR review as the approval gesture, PR comments and labelled issues into the same inbox, _meta/STATUS.md as the reader surface, no Confluence credentials at all Specified
What M8 changes, and what it does not Confluence supplies four capabilities and only the first is storage: the page store, the approval gesture, the feedback channel, and the reader surface. The repo already provides the store, so a repo-native mode is an interaction surface, not a second database. It changes no planner — every planner is already a pure function over state plus an observation — and it inverts one accepted loss: a PR review has an author, so approvedBy stops reading unknown.
10 Common questions

Can I keep editing pages in Confluence?

No, and the tool will not pretend otherwise. A hand edit survives until the page's markdown changes, then it is gone. If a page needs to be editable in Confluence, it does not belong in a DocuMe space.

What happens to an approval when I fix a typo?

It is revoked, the previous approval is archived to history, and the page moves to needs-review. Approval tracks content, and a typo fix is a content change. Banner refreshes, dashboard runs and reparenting are not.

Do I need Claude Code?

Not for the CLI half, which is the whole publish, sync, drift and dashboard story. The plugin is what writes and rewrites pages; without it you write the markdown yourself and everything else works the same.

What if a page uses markdown Confluence cannot express?

It degrades with a named code and a report, or it fails the page outright. Which of the two depends on whether guessing would publish something wrong. docume convert tells you before a publish run does.

Do the diagrams need Node?

Only if you use mermaid. Fences are rendered to SVG and uploaded as attachments, named from a hash of the diagram source, so an unrelated edit elsewhere on the page never renames the attachment. Six diagram families render; anything else fails its page rather than publishing a broken image.

Can two repositories publish to one space?

They can, but orphan detection is per repo: publish --prune reads pages it has state for. Give each repository its own space, or its own subtree, and prune after a full publish rather than alongside a partial one.

Documentation that a build can fail on.

Every claim on this page is asserted somewhere in the suite. That is the argument.
