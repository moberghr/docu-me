# Architecture Principles — DocuMe

## Provenance

Generated by MTK setup-bootstrap on 2026-07-24 on a **greenfield repo**: zero source files existed (`find . -name "*.cs"` empty; repo at commit bb43d9b contained only PLAN.md, GATES.md, README.md, tools/loop/). The repomap evidence pass could not run — there is no code to map. Every principle below is therefore sourced from `PLAN.md` (the approved build plan), not from code evidence. Re-run `/mtk-setup --audit` after M1 lands to replace plan-derived claims with code-derived ones.

## P1 — Two tiers, hard boundary

Deterministic tier = `docume` CLI: runs on deploy/cron, no LLM, cheap, and is the only thing that writes to Confluence. Generative tier = Claude skills (`docs-loop`, `docs-refresh`, `docs-feedback`): always output PRs for human review, never call the Confluence API. Skills invoke the CLI via Bash. Evidence: `PLAN.md` §1 "Design principles", §11.

## P2 — The repo is the source of truth

Confluence is presentation plus human input (labels, comments). Hand edits there are lost on republish; the feedback flow (§9) is the only channel back into the repo. Evidence: `PLAN.md` §1.

## P3 — Core/Cli split

All logic lives in `DocuMe.Core` (library, NuGet); `DocuMe.Cli` is a thin System.CommandLine wrapper over it. Evidence: `PLAN.md` §3 layout, §4.

## P4 — Confluence behind an interface, Cloud-only v1

The REST client is designed behind an interface but only Confluence Cloud is built in v1: a thin custom client on `HttpClient` (~12 endpoints, REST v2 plus v1 where v2 lacks). Spike S1 is **settled** — `Dapplo.Confluence` was measured and rejected. It is alive (1.0.41, January 2026, with a `net10.0` target) but hard-wires its API root to `/rest/api`, the v1 content API, and reaches Atlassian through `Dapplo.HttpExtensions` + Newtonsoft, so it misses §4 on both counts: v2-first, and `Microsoft.Extensions.Http.Resilience` on the transport. The durable record is `ConfluenceClient`'s own remarks. Evidence: `PLAN.md` §1 non-goals, §4, §13 S1; `src/DocuMe.Core/Confluence/ConfluenceClient.cs`.

## P5 — Renderer, not regex

Markdown → Confluence storage format is a custom Markdig renderer (`ConfluenceStorageRenderer : TextRendererBase`), never md→html→regex. The golden-file suite (`tests/golden/`) is the converter's contract. Evidence: `PLAN.md` §7.

## P6 — Hash source-derived content only

`contentHash` is computed from the converted body pre-upload, excludes the injected banner, and is never recomputed from a Confluence read-back (Confluence may rewrite stored XHTML, breaking hash stability). Evidence: `PLAN.md` §5.3, §8, §13 S6.

## P7 — State is machine-owned and committed

`_meta/state.json` in consumer repos holds one entry per page (pageId, hashes, approval, cursors); load/save/migration owned by `DocuMe.Core` State. Approval history is kept for audit (financial-org requirement). Evidence: `PLAN.md` §5.3, §8.

## P8 — One tool, many repos

All repo-specific knowledge lives in the consumer repo (`docume.json`, `_meta/STYLE.md`, page frontmatter); the tool and the skills stay generic. Evidence: `PLAN.md` §1.

## P9 — Single version across artifacts

CLI, Core library, plugin, and GitHub Action release together under one `vX.Y.Z` tag; consumers pin via `dotnet-tools.json`. Evidence: `PLAN.md` §12.
